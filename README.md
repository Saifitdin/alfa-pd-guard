# Модуль безопасности персональных данных

Прокси между системой-потребителем и LLM. Находит персональные данные в запросе,
маскирует их до отправки в модель и восстанавливает в ответе.

```
Система-потребитель ──▶ Модуль ──▶ LLM ──▶ Модуль ──▶ Система-потребитель
                    идентификация        демаскирование
                     маскирование
```

**Главное решение проекта: на горячем пути нет ни одного обращения к LLM.**
Распознавание детерминированное — регулярные выражения, контрольные суммы,
словари и контекстные правила. Поэтому время ответа зависит только от длины
текста и не зависит от чужой доступности: измеренный p99 — **0.47 мс**,
пропускная способность — **1500+ RPS на одном воркере**, 4668 RPS на четырёх.

## Развёрнутый стенд

**https://alfa-pd-guard.onrender.com** — корень ведёт на демо-страницу `/demo`
(два поля и три кнопки: маскирование с разбором по сущностям, восстановление,

`/process`, сводка на `/stats`. Проверено снаружи симулятором проверяющей системы:
30/30 пар, точность 100 %, утечек 0, без ответов 0, `429` 0, latency avg/p95 —
149/205 мс вместе с сетевым round-trip до Франкфурта. Четыре воркера поверх
общего Key Value, поэтому демаскирование не зависит от того, в какой процесс
попал обратный запрос.

Цепочка с AlfaGen с этого стенда не работает: гейтвей отвечает `403` на
запросы из-за рубежа (Render, Франкфурт), тогда как из российской сети тот же
ключ даёт `200`. На стенде цепочка деградирует до заглушки, как задумано;
живой AlfaGen показывается с ноутбука или с российского хостинга.

### Нагрузочное тестирование стенда

Пары «маска → оригинал» по логике Приложения B, генераторы — `bench/loadtest.py`
в несколько процессов с ноутбука (RTT до Франкфурта ~140 мс).

Конфигурация стенда: Pro Plus (4 vCPU), `WEB_CONCURRENCY=4`, Key Value как
общее хранилище.

| нагрузка (процессы × соединения) | RPS | серверная latency avg / p99 | клиентский p95 | точность | ошибки, 429 |
|---|---|---|---|---|---|
| 4 × 64, 45 с | 333 | 3,9 / 46,8 мс | 2 549 мс | 100 % | 0 |
| 8 × 128, 60 с | 521 | 4,5 / 32,2 мс | 5 905 мс | 100 % | 0 |
| **11 × 96, 50 с** | **1 599** | 19,6 / 77,7 мс | 1 430 мс | **100 %** | 0 |
| 11 × 64, 50 с | 1 548 | 67,9 / 760,3 мс | 871 мс | 99,997 % | 0 |
| 12 × 128, 50 с | 681 | 19,0 / 70,6 мс | 6 565 мс | 100 % | 0 |

**Цель 1000 RPS достигнута: 1 599 RPS при точности восстановления 100 %**,
ноль ошибок и ноль `429`. Серверная latency на пике — 19,6 мс в среднем и
77,7 мс на p99, то есть в тринадцать раз ниже потолка в 1 с из ТЗ.

Потолок в этих замерах — генератор, а не стенд. Видно по двум признакам.
Во-первых, клиентская задержка на порядок больше серверной (1 939 мс против
4,5 мс на прогоне 8×128): время уходит в очередь на ноутбуке и в RTT до
Франкфурта (~140 мс), а не в обработку. Во-вторых, рост числа соединений
перестаёт помогать и начинает мешать: 12 × 128 даёт 681 RPS против 1 599 у
11 × 96, потому что генератор упирается в своё ядро на процесс (замеренная
загрузка — 650–710 % из 1 200 % при восьми процессах, то есть каждый процесс
близок к пределу одного ядра). Лучший результат получается, когда процессов
столько же, сколько ядер у ноутбука, а соединений на процесс умеренно.

Единственное несовпадение за все прогоны — 1 пара из 39 299 на 11 × 64
(99,997 %). Локальный `docker compose` с той же конфигурацией (4 воркера +
Redis на одной машине, без сети между ними) даёт 4 668 RPS.

**Как воспроизвести конфигурацию.** `render.yaml` в репозитории описывает её
целиком:

1. Key Value (план starter, 256 МБ, `allkeys-lru`), его Internal URL в
   `PDGUARD_REDIS_URL`.
2. `PDGUARD_STORE_BACKEND=redis` и общий `PDGUARD_STORE_KEY` (32 байта base64,
   задаётся в панели как секрет).
3. `WEB_CONCURRENCY=4` — uvicorn подхватит без правки команды запуска.

Без Redis несколько воркеров запускать нельзя: прямой и обратный запрос по
одному `payload_id` попадут в разные процессы. Сервис на такой конфигурации
откажется стартовать с понятным сообщением — это защита от тихой порчи
демаскирования.

#### Что сломалось на стенде и как это устроено теперь

Первый прогон на этой конфигурации дал 21 % несовпадений, а затем стенд начал
отвечать `internal_error` на каждый запрос при зелёном `/health`. Обе аварии —
про соединения к Key Value, и обе закрыты:

* пул `redis-py` рос по числу одновременных запросов и вчетвером перебирал
  лимит соединений инстанса (250 на starter); дальше падала каждая команда.
  Теперь `BlockingConnectionPool` с `max_connections=40` на воркер
  (`PDGUARD_REDIS_MAX_CONNECTIONS`) ждёт свободное соединение вместо отказа;
* соединения, закрытые Key Value по простою, роняли каждую следующую команду
  до перезапуска процесса. Теперь `health_check_interval=30`, `socket_keepalive`
  и два ретрая с экспоненциальной паузой;
* если Redis всё же недоступен, воркер продолжает работать на локальной памяти
  вместо `500` на каждый запрос. Маскирование — единственное, что защищает ПД —
  не отказывает никогда; демаскирование в этом режиме даёт честное «записи нет»
  и само восстанавливается. Причина отката видна в `/health` как `store_error`.

## Проверка за две минуты

Подробный сценарий для жюри — в [docs/JURY.md](docs/JURY.md). Самое короткое:

**1. Маскирование.** Первый запрос с новым `payload_id`:

```bash
curl -s -X POST http://localhost:8000/process \
  -H 'Content-Type: application/json' \
  -d '{"payload":"Клиент Иванов Иван Иванович, паспорт 4509 123456","payload_id":"check-1"}'
```

```json
{"result": "Клиент И. И. И., паспорт 45** ****56"}
```

**2. Демаскирование.** Второй запрос с тем же `payload_id`:

```bash
curl -s -X POST http://localhost:8000/process \
  -H 'Content-Type: application/json' \
  -d '{"payload":"Клиент И. И. И., паспорт 45** ****56","payload_id":"check-1"}'
```

```json
{"result": "Клиент Иванов Иван Иванович, паспорт 4509 123456"}
```

**3. Ловушка.** Публичная персона и адрес отделения остаются нетронутыми:

```bash
curl -s -X POST http://localhost:8000/v1/mask \
  -H 'Content-Type: application/json' \
  -d '{"text":"Поэт Александр Пушкин упомянут в письме. Отделение банка: г. Москва, ул. Каланчевская, д. 27"}'
```

В ответе `detected` будет пустым: ни имя классика, ни адрес офиса персональными
данными клиента не являются.

**4. Вся цепочка с LLM.** Видно, что именно ушло в модель:

```bash
curl -s -X POST http://localhost:8000/v1/llm/chat \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Клиент Иванов Иван Иванович, карта 4276 3800 1234 5679, помоги составить ответ"}'
```

Поле `prompt_sent_to_llm` — это ровно тот текст, который получила внешняя модель.
Поле `answer` — ответ после обратной подстановки.

## Что распознаётся

Все 17 обязательных типов из ТЗ:

| Тип | Ключ | Как определяется |
|---|---|---|
| ФИО | `fio` | словарь имён + морфология отчеств и фамилий + контекст, со стоп-листом публичных персон |
| Дата рождения | `birth_date` | 11 форматов, тип уточняется ближайшим маркером |
| Место рождения | `birth_place` | маркеры «место рождения», «уроженец» |
| Серия и номер паспорта | `passport_rf` | с разделяющими словами и без них |
| Гражданство | `citizenship` | маркеры «гражданство», «гражданин» |
| Орган, выдавший паспорт | `passport_issuer` | текст после «выдан» до запятой или даты |
| Код подразделения | `department_code` | `ХХХ-ХХХ` рядом с паспортным контекстом |
| Дата выдачи паспорта | `passport_issue_date` | те же форматы, маркер «выдан» |
| Водительское удостоверение | `driver_license` | `ХХХХ ХХХХХХ` + контекст |
| Адрес | `address` | сборка из компонентов, стоп-лист адресов отделений |
| Email | `email` | шаблон RFC-подобный |
| Телефон | `phone` | форматы РФ, с кодом страны и без |
| ИНН | `inn` | **контрольная сумма** для 10 и 12 знаков |
| Номер карты | `card_number` | **алгоритм Луна + диапазон BIN** |
| CVV | `cvv` | контекст, по умолчанию только вместе с картой |
| ПИН-код | `pin` | контекст, по умолчанию только вместе с картой |
| Имя держателя карты | `card_holder` | латиница капсом в карточном контексте |

Сверх обязательного перечня: СНИЛС (с контрольной суммой), заграничный паспорт,
номер банковского счёта, дата без контекста.

### Как отличается клиент от классика

Ложные срабатывания — отдельная инженерная задача, а не побочный эффект. Работают
четыре независимых механизма:

1. **Контрольные суммы.** Луна для карт, проверочные разряды для ИНН и СНИЛС.
   Примерно каждый десятый случайный набор из 16 цифр проходит Луна, поэтому
   дополнительно проверяется диапазон BIN — номер заказа `1234 5678 1234 5670`
   картой не считается.
2. **Стоп-листы** публичных персон и адресов отделений (`data/stoplist.yaml`).
3. **Контекстные маркеры.** «Поэт», «написал», «памятник» подавляют находку;
   «клиент», «паспорт», «на имя» — подтверждают. Однофамилец классика
   с клиентским контекстом распознаётся: «Клиент Пушкин Андрей Викторович» — это ПД.
4. **Порог компонентов.** Одиночное «г. Казань» адресом не считается.

## Настройка

Всё поведение задаётся двумя YAML-файлами и применяется без перезапуска:

```bash
curl -X POST http://localhost:8000/admin/reload
```

### Настройка в пяти предложениях

Система-потребитель описывается записью в `config/systems.yaml` с уникальным
`api_key`, и она получает доступ к модулю, пока у неё `enabled: true`. Поле
`pd_types` перечисляет типы ПД, которые для этой системы ищутся и маскируются,
либо содержит `[all]`. Поле `masking_strategy` выбирает вид маски — `partial`,
`full`, `token` или `synthetic`, — а `demasking_enabled` разрешает или запрещает
системе обратное преобразование. Новый тип ПД добавляется записью в
`config/pd_types.yaml` (при необходимости — с регулярным выражением в
`custom_patterns`), а публичные персоны и адреса отделений — в
`data/stoplist.yaml`. После любой правки достаточно вызвать
`POST /admin/reload`, перезапуск не нужен.

### `config/systems.yaml` — системы-потребители

```yaml
systems:
  - id: alfagen-chat
    api_key: demo-key-alfagen-chat
    enabled: true                 # вкл/откл доступ системы к модулю
    masking_strategy: token       # partial | full | token | synthetic
    demasking_enabled: true       # разрешено ли обратное преобразование
    pd_types: [all]               # либо явный список типов
```

Система определяется по заголовку `X-API-Key` (или `X-System-Id`). Неизвестная и
отключённая системы получают `403` и до обработки текста не доходят — это и есть
«ограниченный список систем» из ТЗ.

Посмотреть текущие политики: `GET /admin/systems`
Отключить систему на лету: `POST /admin/systems/{id}/toggle` с `{"enabled": false}`

### `config/pd_types.yaml` — справочник типов

Новый тип ПД добавляется записью в файл, без правки кода:

```yaml
custom_patterns:
  foreign_passport:
    pattern: '(?<![\d])\d{2}\s?\d{7}(?![\d])'
    markers: [загранпаспорт, заграничный паспорт]
    confidence: 0.9
```

Там же настраивается вид частичной маски — сколько знаков оставить видимыми:

```yaml
  card_number:
    partial: {head: 4, tail: 4}   # 4276 **** **** 5679
```

### Словари

`data/names_ru.txt` — личные имена, `data/stoplist.yaml` — публичные персоны,
адреса отделений и организации. Пополняются текстом, подхватываются по
`/admin/reload`.

## Стратегии маскирования

Выбираются для каждой системы отдельно.

| Стратегия | Результат | Когда применять |
|---|---|---|
| `partial` | `Клиент И. И. И., паспорт 45** ****56` | совпадает с примером из контракта ТЗ |
| `full` | `Клиент **. **. **., паспорт **** ******` | максимальная строгость |
| `token` | `Клиент [FIO_1], паспорт [PASSPORT_RF_1]` | **рекомендуется для реального LLM-контура** |
| `synthetic` | `Клиент Петров Пётр Петрович, паспорт 7712 884503` | аналитика на обезличенных, но реалистичных данных |

Токен ФИО несёт грамматическую подсказку рода — `[FIO_1:F]` / `[FIO_1:M]`, —
без которой модель писала «Уважаемый Петрова Анна Сергеевна». Пол человека не
идентифицирует, а обращение делает правильным; выводится по отчеству, фамилии
и имени, при неуверенности суффикс не ставится. Демаскирование принимает токен
и с суффиксом, и без него — модель вправе его потерять. Синтетика подбирает
имя того же рода. Отключается через `token_gender_hint: false`.

В обращении подставляются имя и отчество, а не полное ФИО: «Уважаемая Анна
Сергеевна», как принято по этикету. Форму выбирает модуль при демаскировании
двумя независимыми путями — по явной просьбе модели (`[FIO_1:F:short]`) либо по
контексту, когда токен стоит сразу после «Уважаемая», «Здравствуйте», «Добрый
день». Второй путь не зависит от того, послушалась ли модель. Вне обращения
(«договор на имя …») остаётся полное ФИО; без отчества подставляется одно имя;
если имя не распознано — полная форма.

Про `token` стоит сказать отдельно: обрывки цифр вида `45** ****56` модель путают,
а осмысленный плейсхолдер сохраняет структуру запроса и не даёт коллизий при
обратной подстановке. `synthetic` даёт стабильную подстановку — одно и то же
значение всегда заменяется одинаково, поэтому в тексте сохраняются связи.

### Контекстное маскирование

ПИН-код сам по себе человека не идентифицирует, а ПИН вместе с номером карты —
идентифицирует. Правило настраивается:

```yaml
combination_rules:
  pin: [card_number]
  cvv: [card_number]
```

«Мой пин-код 4321» останется как есть. «Карта 4276 3800 1234 5679, пин-код 4321» —
будет замаскировано целиком.

## Демаскирование

Соответствие хранится по `payload_id`: зашифрованное (AES-GCM), с TTL и
ограничением размера, вытеснение — LRU.

Два пути восстановления:

* **Точный** — пришла ровно та маска, которую отдали: возвращается сохранённый
  оригинал, позиции знаков совпадают побайтово.
* **Общий** — обратная подстановка по карте плейсхолдеров. Нужен для ответа LLM,
  где маска встречается внутри сгенерированного текста: на `[FIO_1]` в ответе
  модели подставится исходное ФИО.

Эндпоинт идемпотентен: повторный прямой запрос с тем же `payload_id` снова вернёт
маску, а не примет её за обратный вызов. Это важно, потому что проверяющая
система делает до двух ретраев.

## Производительность

Две конфигурации, обе измерены на MacBook Pro M4 Pro.

**Один процесс, хранилище в памяти** (Python 3.14, нативно):

| Показатель | Значение | Цель по ТЗ |
|---|---|---|
| Latency p99 (серверная) | **0.47 мс** | ≤ 1000 мс |
| Latency p95 | 0.34 мс | — |
| Latency avg | 0.28 мс | — |
| RPS, один воркер | **1523** | 1000 |
| TPS | 38 079 токенов/с | — |
| Ядро без HTTP, avg / p99 | 0.20 / 0.65 мс | — |
| Текст 100 000 токенов | 898 мс | без падения |
| Точность roundtrip | 100% (33 429 запросов, ошибок 0) | 95% |

Числа — из последнего прогона после всех правок; более ранний замер той же
конфигурации давал 2262 RPS при p99 0.28 мс, разница объясняется фоновой
нагрузкой на ноутбуке, а не кодом (ядро между замерами стало быстрее). В README
оставлен консервативный результат.

**Docker compose: 4 воркера + Redis** (внутри VM на 4 ядра, клиент снаружи VM):

| Показатель | Значение |
|---|---|
| RPS суммарно | **4668** |
| Latency p99 | 22.9 мс |
| Latency p95 | 11.4 мс |
| Точность roundtrip | 100% (4506 пар, ошибок 0) |

Latency в Docker выше на порядок — и это ожидаемо: добавились сетевой вызов
в Redis на каждый запрос, граница виртуальной машины и конкуренция четырёх
воркеров с Redis за те же 4 ядра. Размен осознанный: общее хранилище — цена
за горизонтальное масштабирование и корректность демаскирования между
процессами. До целевой секунды всё равно остаётся сорокакратный запас.

Показатель `rps` в `/stats` — это среднее за 60-секундное окно, а не мгновенная
скорость: после всплеска нагрузки он какое-то время занижен. Пиковые значения
меряются инструментами из `bench/`.

Воспроизвести:

```bash
python bench/contract_check.py --url http://localhost:8000          # самопроверка контракта
python bench/bench_pipeline.py --iterations 3000                     # ядро без HTTP
python bench/loadtest.py --url http://localhost:8000 --duration 30   # пары по контракту
python bench/rawclient.py --connections 40 --duration 20             # потолок пропускной способности
```

### Самопроверка контракта

`bench/contract_check.py` повторяет правила Приложения B дословно: пары по
`payload_id`, таймаут 10 с, до трёх попыток, учёт `Retry-After`, остановка после
пяти невалидных ответов подряд. Дополнительно проверяется то, ради чего модуль
существует: что в маске не осталось исходных данных.

```
Пар обработано:          30
Маскирование ответило:   30/30
Демаскирование точное:   30/30  (100.0%)
Утечек ПД в маске:       0
Latency avg / p95:       2.3 / 3.1 мс
РЕЗУЛЬТАТ: контракт пройден
```

Формат обмена сверен с эталонной реализацией `process-test.holydev.space`
на одиннадцати сценариях — обычный запрос, пустые значения, отсутствующие поля,
неверный тип, лишние поля, юникод, строка на 200 КБ, битый JSON и пустое тело.
Коды ответов и форма JSON совпадают везде, включая `422` с `{detail: [...]}`.

Полезное наблюдение: эталон **ничего не маскирует**, он возвращает вход без
изменений — как и написано в ТЗ, он демонстрирует только формат обмена. Тот же
чекер на эталоне показывает 10/10 по протоколу и 9 утечек из 10 по содержимому.
Ориентироваться на него как на образец маскирования нельзя, правила берутся
из ТЗ.

Метрики в реальном времени: `GET /stats` (человекочитаемо) и `GET /metrics`
(Prometheus: `pdguard_latency_seconds`, `pdguard_requests_total`,
`pdguard_tokens_total`, `pdguard_pd_entities_total`).

Честная оговорка: 2262 RPS — это потолок **одного** воркера на ноутбуке, и он уже
вдвое перекрывает цель. Для запаса и отказоустойчивости в docker-compose поднимается
несколько воркеров с общим хранилищем в Redis — без общего хранилища прямой и
обратный запрос могут попасть в разные процессы, и демаскирование сломается.

## Безопасность и наблюдаемость

* **В логи не попадают ни исходный текст, ни значения ПД** — только типы,
  количество, длины и тайминги. Поверх стоит предохранитель `PDRedactionFilter`,
  который вырезает из любого лог-сообщения то, что похоже на карту, телефон,
  email, паспорт или ИНН, — на случай ошибки разработчика.
* Логи структурные (JSON), по каждому запросу пишется список выявленных типов ПД —
  требование п. 4.1 ТЗ.
* Хранилище соответствий шифруется AES-GCM. Ключ берётся из `PDGUARD_STORE_KEY`.
  Если переменная не задана, ключ генерируется на старте — это допустимо только
  для одного процесса с хранилищем в памяти. При `PDGUARD_STORE_BACKEND=redis`
  общий ключ **обязателен**, и сервис откажется стартовать без него: у каждого
  воркера был бы свой ключ, и запись одного процесса не расшифровалась бы
  другим. Сгенерировать ключ:
  `python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"`
* Доступ ограничен списком систем; отключение системы мгновенное.
* При недоступности LLM или Redis сервис деградирует, а не падает: включается
  локальная заглушка модели, хранилище откатывается на память процесса.
* Ошибки возвращаются машиночитаемо: `{"error": "payload_too_large", ...}`,
  перегрузка — `429` с `Retry-After`.

Пример строки лога:

```json
{"ts":"2026-09-23T17:40:12+0300","level":"INFO","logger":"pdguard.process",
 "message":"mask","payload_id":"check-1","system_id":"loadtest","strategy":"partial",
 "pd_types":["fio","passport_rf"],"entities":2,"chars":48,"latency_ms":0.214}
```

## Подключение к AlfaGen

Цепочка `/v1/llm/chat` проверена на корпоративной модели AlfaGen
(`deepseek-ai/DeepSeek-V4-Flash-0731`). Для подключения нужен файл `.env` в
корне проекта:

```
PDGUARD_LLM_URL=https://alfagen.alfabank.ru/continue-dev/
PDGUARD_LLM_KEY=<ключ из раздела Enterprise Vibe Coding на портале AlfaGen>
PDGUARD_LLM_MODEL=deepseek-ai/DeepSeek-V4-Flash-0731
```

Файл подхватывается автоматически и нативным запуском, и `docker compose`.
Он в `.gitignore` и `.dockerignore`, а `make zip` откажется собирать архив, если
`.env` в него попал: в артефактах сдачи ключей быть не должно. Без файла цепочка
работает на локальной заглушке — деградация, а не отказ.

Три особенности, на которых легко потерять время:

* **Сертификат.** AlfaGen выпущен под Russian Trusted CA, которого нет в пакете
  `certifi`, а Python-клиент смотрит именно в него, а не в связку ключей
  системы. Публичный корневой сертификат лежит в `certs/` и склеивается с
  `certifi` в бандл, которому доверяет **только** LLM-клиент. Системное
  доверие не меняется.
* **`stream: false` обязателен.** Без явного поля гейтвей отвечает `400` с
  пустым телом, хотя `/models` при этом работает. Адаптер всегда его передаёт.
* **Базовый URL.** В инструкции даны два варианта — `/continue-dev/` и
  `/continue-dev/v1`; адаптер пробует оба.

И одно наблюдение из живого прогона, важное для выбора стратегии. На маске
`partial` модель, получив «Клиент И. И. И.», ответила «Уважаемый Иван
Иванович!» — угадала каноническое имя по инициалам. Для произвольного клиента
это невозможно, но сама попытка показывает: частичная маска оставляет модели
пищу для догадок. Стратегия `token` отдаёт модели `[FIO_1]`, она пишет
«Уважаемый [FIO_1]», и настоящее имя подставляется уже на нашей стороне.
Поэтому для систем, ходящих в LLM, в конфигурации по умолчанию стоит `token`.

У токенизации есть и цена, тоже видная на живом прогоне: получив
`[CARD_NUMBER_1]`, модель не смогла назвать последние цифры карты и написала
«ending in [last 4 digits of CARD_NUMBER_1]», тогда как на маске `partial`
(«4276 **** **** 5679») корректно указала «5679». Это не дефект, а размен:
`token` не оставляет модели ничего, `partial` оставляет ровно то, что ей нужно
для ответа. Выбор — за политикой системы-потребителя; смешанная стратегия по
типам (имена токенизировать, хвост карты показывать) — в плане развития.

## API

| Метод | Назначение |
|---|---|
| `POST /process` | контракт хакатона: `{payload, payload_id}` → `{result}` |
| `POST /v1/mask` | маскирование с отчётом: что найдено, где, с какой уверенностью |
| `POST /v1/demask` | явное обратное преобразование |
| `POST /v1/llm/chat` | демонстрация цепочки с LLM |
| `GET /health` | проба живости |
| `GET /stats` | сводка Latency / RPS / TPS |
| `GET /metrics` | Prometheus |
| `GET /admin/systems` | политики систем-потребителей |
| `GET /admin/pd-types` | справочник типов ПД |
| `POST /admin/systems/{id}/toggle` | включить/отключить систему |
| `POST /admin/reload` | перечитать конфигурацию и словари |

Переменные окружения: `PDGUARD_STORE_BACKEND` (`memory`/`redis`),
`PDGUARD_REDIS_URL`, `PDGUARD_STORE_TTL`, `PDGUARD_REQUIRE_API_KEY`,
`PDGUARD_DEFAULT_SYSTEM`, `PDGUARD_MAX_CONCURRENCY`, `PDGUARD_LOG_LEVEL`,
`PDGUARD_LLM_URL`, `PDGUARD_LLM_KEY`.
